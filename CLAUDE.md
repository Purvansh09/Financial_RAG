# CLAUDE.md

## Project overview
Financial Document RAG: a web app where users upload financial documents (annual reports, SEBI filings, earnings call transcripts) and ask questions in plain English. Answers are generated only from retrieved passages and always cite the source document and page number.

This is a portfolio project for AI/ML roles. Code quality, measurable results, and a clear README matter as much as the app itself.

## Goals
1. Working baseline: ingest PDFs, retrieve relevant chunks, answer with citations, Streamlit UI, deployed.
2. Evaluation: hand-labeled question set with retrieval hit rate and answer faithfulness metrics.
3. Improvements, each measured against the baseline: hybrid search (BM25 + vectors), reranking, table handling.

## Tech stack
- Python 3.11+
- PDF parsing: PyMuPDF (text), pdfplumber or Camelot (tables, later phase)
- Embeddings: sentence-transformers (`bge-small-en-v1.5` or similar)
- Vector store: FAISS or Chroma
- Keyword search: `rank_bm25` (Phase 6)
- LLM: Claude via the Anthropic API (model name set in config, not hardcoded)
- UI: Streamlit
- Evaluation: RAGAS or a simple LLM-as-judge, plus plain retrieval hit rate
- Deployment: Hugging Face Spaces

## Core conventions
- Every chunk carries metadata: `company`, `year`, `doc_type`, `source_file`, `page`. Never drop page numbers; citations depend on them.
- Chunk size is about 500 tokens with 50-100 token overlap. Values live in `config.py`.
- The generation prompt must: answer only from the provided context, cite pages, and say "not found in the documents" when the context does not support an answer. Never let the model answer from its own knowledge.
- Keep retrieval and generation separate so each can be evaluated on its own.
- No API keys in code. Use `.env` and keep `.env.example` updated.
- Use type hints and short docstrings. Keep functions small and testable.
- Prefer plain Python over heavy frameworks. LangChain/LlamaIndex are optional; if used, keep them thin so the logic stays visible.

## Phases (follow in order)
0. Setup: repo, environment, 8-10 real documents
1. Ingestion and chunking
2. Indexing and retrieval
3. Answer generation with citations
4. Streamlit UI and first deploy (baseline complete)
5. Evaluation: 40-50 labeled questions, baseline metrics recorded
6. Retrieval upgrades: hybrid search, reranker
7. Table handling: extract tables, index as separate chunks with title and units
8. Polish: README, architecture diagram, results table, demo

Do not start a later phase until the checkpoint of the current one is met.

## Evaluation rules
- Record baseline metrics before changing retrieval. Every change gets a before/after row in `eval/results/`.
- Metrics: retrieval hit rate @k (did the correct page's chunk appear in the top k?) and answer faithfulness (is every claim supported by the retrieved context?).
- Include a set of table-specific questions and a set of unanswerable questions (the correct response is "not found").
- Questions and labels are written by hand from the real documents, not generated by an LLM.
